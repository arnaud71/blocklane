# Read-only API and adapters

`server/index.ts` starts the native Node 24 HTTP server. Importing `createApp` from `server/app.ts` constructs the server without opening a port, for tests or another entry point. `npm start` uses `tsx` and loads `.env` when present.

## Shared event streams

`SnapshotService` owns a lazy `eventStreams` reader: one native Node 24 connection per network, shared between live visitors. The aggregate `eventFlow` context decorates snapshots without renewing their block timestamps and remains separate from the complete `poolFlow` inventory. Bitcoin also reuses received details for its arrival reserve described below, without per-hash enrichment calls. The browser retains its usual HTTP API; no provider connection or key is passed to it. `dispose()` closes connections and the watchdog when the server stops.

Optional server variables `BITCOIN_EVENTS_WS_URL` and `ETHEREUM_EVENTS_WS_URL` accept WSS, or WS on loopback, without credentials or fragments; an empty value disables the corresponding network. Without an explicit variable, mempool.space and Ethereum PublicNode are enabled only if the associated HTTP provider remains the default. A custom endpoint receives a distinct sanitized label. A provider or HTTP transport injected in tests does not open a real stream; a test `EventFlowReader` or `socketFactory` can be supplied separately.

Bitcoin requests `track-mempool: true` and reads `mempool-transactions`: `added` contains transaction objects, `removed` and `mined` contain identifiers, and `replaced` contains old identifiers with their replacements. This stream is independent of the first projected block; the first sequence establishes a baseline, and only consecutive sequences open a period. Production `eventFlow.method` is now `mempool-transactions`; the contract still accepts `mempool-txids` for compatibility. Ethereum checks `eth_chainId` before requesting one `newPendingTransactions` subscription in hash format, then waits for acknowledgement. Connection timestamps and an opaque numeric period identifier prevent replay of an old sequence, including after process restart. Reconnection and resynchronization invent no catch-up history.

Batches publish at most every three seconds, with twelve points over roughly one minute. At most twenty thousand private identifiers are deduplicated over sixty seconds; the outside-selection partition is fixed at first publication. Limits: two MiB per Bitcoin message, 256 KiB for Ethereum, eight MiB per minute and one hundred messages per second per network, retained across connections. Connection timeout is eight seconds, silence thirty seconds, closure after one minute without a reader, and backoff capped at thirty seconds. A read gap over fifteen seconds establishes a new baseline rather than replaying an old surge. Messages establish neither exhaustive presence nor confirmation. Public providers may remain silent or refuse subscriptions: availability is not guaranteed.

### Reserve of real Bitcoin arrivals

`bitcoinLiveArrivals` retains at most **384 compact details** from the continuous stream's latest arrivals. Fees must be valid integer satoshis, and virtual size a multiple of one quarter byte between 1 and 1,000,000 vB. A complete object uses `weight / 4`, like `stripTransaction`; an already compact object may supply `vsize`. The published rate is the transaction's own fee divided by this size, without the package or acceleration effective rate. No amount, contract classification, input or output is inferred; `kind: transfer` remains Bitcoin's generic category. Raw bodies are not retained and no per-ID HTTP request is made.

Ordering follows observed receipt, newest first, without moving an already retained ID when its metadata changes. The latest valid consecutive delta, even empty, renews the group's presence timestamp; reading the reserve does not redate it. It expires after sixty seconds without such a delta. Disconnection, loading, a sequence gap or rollback clears it. The removed, mined and replaced fields remove affected details without producing confirmed evidence; a replacement lacking added details is not invented.

The adapter reserves these **384 places inside the 1,920 pending limit**, then fills remaining places from the GBT base selection or its fallbacks, deduplicating IDs. A partial reserve leaves its unused places available. The result is a mixed sample, not a global ranking or guaranteed inclusion. `Snapshot.bitcoinArrivals` carries the source, `mempool-transactions` method, independent timestamp and up to 384 pending IDs actually represented. It replaces neither `sampling`, `poolObservation` nor block confirmations. An arrival observed on this stream is not declared present in another RPC's inventory. An older displaced detail can remain a historical observation within existing budgets; Ethereum and overall limits remain unchanged.

Sources: [mempool.space WebSocket protocol](https://mempool.space/docs/api/websocket), [delta format](https://github.com/mempool/mempool/blob/master/backend/src/mempool.interfaces.ts#L97-L103), [added-object emission](https://github.com/mempool/mempool/blob/master/backend/src/api/websocket-handler.ts#L663-L668), [official compaction](https://github.com/mempool/mempool/blob/master/backend/src/api/common.ts#L749-L758).

## HTTP contract

- `GET /api/health` checks the HTTP process and returns `{ "status": "ok", "service": "blockchain-observer", "readOnly": true }`. It does not guarantee external-provider availability.
- `GET /api/snapshot?chain=bitcoin&mode=live` returns a `Snapshot` validated by `shared/model.ts`. Chains: `bitcoin`, `ethereum`. Modes: `live`, `demo`. Defaults: `bitcoin`, `live`. Unknown, duplicate or invalid parameters return HTTP 400. Methods other than GET return HTTP 405.
- A provider failure produces HTTP 200 with `status: stale` or `unavailable`, retaining an explicit network state. An unexpected internal error produces a sanitized HTTP 500.

Blocks use Unix seconds (`timestamp`); snapshots use Unix milliseconds (`observedAt`). An expired snapshot retains its last successful observation time. HTTP responses expose neither configuration URLs nor provider error responses.

### Prioritized Bitcoin candidate — 15 October 2026

`adapters/bitcoinTemplate.ts` adds an optional `getblocktemplate` read on the same `BITCOIN_RPC_URL` as the Bitcoin pool; an empty value disables these RPC capabilities. Priority becomes **GBT node candidate → RPC-pool ranking → first mempool.space projected block → recent transactions**. Refusal, timeout, invalid response, different head or expiry enables an explicit fallback without replacing live data with simulation. The GBT source represents that node's proposal, never proof that a pool is mining it or a guaranteed next block.

`createBitcoinTemplateReader` returns a synchronous reader that launches at most one background collection per instance. It checks `getblockchaininfo` (`main`, initial synchronization finished), then requests `getblocktemplate({"rules":["segwit"]})` within a **total eight-second budget**. The GBT response is limited to **16 MiB and 30,000 transactions**; the chain-information read to 64 KiB. Attempts are separated by at least **fifteen seconds after completion**, and the candidate expires **thirty seconds after receipt**. Visitors share this reader, independent of the three-second blockchain cache and complete-pool reader. Blockchain collection does not wait for it. Injected transports remain isolated: a provider test explicitly injects this reader without triggering an implicit new public request.

RPC envelopes and IDs, hexadecimal shapes, integer-satoshi fees, BIP141 weights, dependency indices pointing to preceding transactions, and size/weight sums are checked before any truncation. A parent may appear repeatedly in `depends` when multiple inputs spend its outputs; only a zero, out-of-bounds or non-preceding index is rejected. Total non-coinbase transaction weight must exceed neither the declared limit nor four million WU. The data's double SHA256 must match the witness hash; the node still supplies the SegWit `txid`. No extra script parser or Bitcoin consensus validator is introduced. Raw data is discarded after checking; only metadata, complete internal membership and up to **1,920 members ranked by highest own fee per `weight / 4`** remain in memory. Exact ranking before rounding does not reproduce CPFP packages; parents may be outside the visible sample.

Before emitting the snapshot, `bitcoin.ts` compares candidate height and parent against the latest REST block. Expiry during catch-up triggers one new collection using fallbacks, after tracking returns to its 4,096-ID limit. `Snapshot.blockTemplate` carries `{ source, observedAt, height, previousBlockHash, transactionCount, weight, weightLimit, medianFeeSats?, selectedTransactionIds }`, separately from `sampling`, which can describe the independent RPC inventory while GBT is active. Public IDs intersect candidate members with up to 1,920 current IDs and tracked IDs, limited to **4,096**, with current IDs first. `transactionCount` and `weight` describe the complete candidate **excluding coinbase**; the mempool count comes from the usable RPC inventory, otherwise REST `/mempool`, with that provenance stated. A candidate is never inclusion evidence.

The reader calculates `medianFeeSats` using `BigInt` over every non-coinbase transaction fee before selecting the top 1,920, without a new RPC call or retained raw data. The current server emits the field, but it remains optional in the contract for compatibility. It is `null` for an empty candidate; otherwise it contains satoshis from zero to 2,100,000,000,000,000 in steps of 0.5. The mean of the central two values may produce half a satoshi; zero is a real median, not absence. This aggregate describes proposed fees, not paid fees or a mempool median.

In the scene, the stationary first Bitcoin wagon represents the complete candidate: `transactionCount`, `weight / 4` vB and `100 × weight / weightLimit`. Known members remain individual; a static SVG group represents the rest without new identifiers, individual metadata or selection options. The grouped count subtracts unique `pending` members actually present throughout the scene, including platform and arrivals, rather than merely the public-ID array's length. The second wagon remains estimated. The group disappears on fallback, expiry and as soon as departure preparation starts; projections recover sampled counts, while real departures use the verified block percentage and included tracked passengers. Parent, reorganization, availability and independent age constrain this view. A proposed group never becomes confirmation. The current contract retains at most **3,840 residents per chain**, including a fixed 1,920 historical reserve, for 1,920 current transactions and 1,944 objects per response. The base selection from candidate and independent inventory may reserve 384 details outside the candidate, or more if the candidate supplies fewer than 1,536 details. The final selection then prioritizes real arrivals within the same 1,920 limit; other components may therefore shrink. Deferred admissions remain bounded to 1,920; the departure cohort to 6,272 and preparation to 10,112 temporary residents. No HTTP route, new key, environment variable, dependency or persistent memory is added; Canvas surfaces retain their budgets. Sources: [Bitcoin Core GBT](https://bitcoincore.org/en/doc/30.0.0/rpc/mining/getblocktemplate/), [mining guide](https://developer.bitcoin.org/devguide/mining.html#getblocktemplate-rpc), [Bitcoin Core 30's `depends` list](https://github.com/bitcoin/bitcoin/blob/v30.0/src/rpc/mining.cpp#L850-L856), [HTTP contract](../docs/api.md#node-bitcoin-candidate--blocktemplate). It adds no account or receipt call. Children and parents share the 4,096-identifier tracking limit and thirty-minute lifetime; an expired parent may leave an unknown marker without a hash on its still-tracked child.

Pool collection is anchored to its head and branch generation. Context is published only for a compatible head, with the pool's original timestamp and the same source/timestamp as `sampling` and `poolObservation`. After a head change, renewal waits for the usual cadence; no early call is added. Public context remains usable for at most sixty seconds. The root, unobserved, gap, unknown, pending, queued and confirmed states have the constraints detailed in the [HTTP contract](../docs/api.md#ethereum-dependencies--ethereumdependencies). A known unadmitted parent blocks its child; a replaced parent updates the edge. Exact journal evidence resolves the old parent, without inferring from a higher nonce alone. The first pending nonce whose predecessor has never been observed remains an explicitly uncertain estimate. A reorganization invalidates incompatible evidence. This context improves animation without claiming to reveal validator construction. ### Late Ethereum inclusions

The service compares new candidates with identifiers from the sixteen recently read blocks, under an overall limit of 65,536 identifiers. It also progressively checks retained identifiers lacking evidence, in the background, without waiting for receipts before responding to the main collection. Shared process budget: sixteen identifiers per pass, two concurrent reads, at least fifteen seconds after the previous pass finishes, at least sixty seconds between attempts for one identifier. Never-tried identifiers have priority so a permanently unknown prefix cannot monopolize the budget. A candidate still present becomes eligible after thirty seconds.

`eth_getTransactionReceipt` uses the fixed configured Ethereum RPC, with a 256 KiB response limit and eight-second timeout. The requested hash, block hash and height must match a canonical block freshly read by number and containing that identifier; this block retains the ordinary two-MiB limit. Execution failure still counts as inclusion. Null, invalid, oversized or failed responses remain without evidence, and a branch change invalidates in-flight results. The journal remains bounded to sixteen blocks and 4,096 identifiers: the latest block is reserved, then fifteen proofs follow discovery order. Tracking, results and retries remain bounded by tracked identifiers and their lifetimes.

At best, this budget permits 64 checks per minute; network conditions, errors and expiry reduce that rate. It does not guarantee checking all 4,096 identifiers within thirty minutes. Restart clears server tracking and does not recover identifiers retained only in the browser. No new endpoint or persistent storage is added. See the [journal contract](../docs/api.md#inclusion-journal), [decision](../docs/architecture.md) and [results](../docs/validation.md).

### Highest-fee complete-pool sample and updates — 15 October 2026

The server attempts an optional complete provider-pool observation, shared by visitors, then transmits only **up to 1,920 retained transactions**, counts and observation metadata. Bitcoin retains a compact pool table in memory for updates; Ethereum retains a compact form of every `pending` candidate for thirty seconds to update prices against the new base fee. The original RPC body is neither sent to the browser nor durably stored. An invalid, truncated, inconsistent or over-limit read leaves the explicit fallback in place, without a fake complete ranking.

As a GBT fallback, **Bitcoin** defaults `BITCOIN_RPC_URL` to `https://bitcoin-rpc.publicnode.com`. An empty value disables this capability. An initial batch reads `getblockchaininfo` and `getrawmempool(true)`, rejects any chain other than `main` or a node in initial synchronization, then builds a table limited to **100,000 transactions**. Ranking compares exact base fees per BIP141 weight (`weight / 4`) before rounding to sat/vB; it ignores fee adjustments, node-policy-adjusted `vsize` and CPFP packages. Size used for drawn capacity remains `weight / 4`, distinct from a potentially policy-adjusted `vsize`.

Subsequent Bitcoin collections request `getrawmempool(false, true)`, a validated inventory of identifiers and sequence number, limited to **eight MiB**: disappeared identifiers are removed from the table and only newcomers receive `getmempoolentry`. A collection handles at most **500 additions**, in batches of **25**, with at most **two concurrent batches** and **128 KiB per batch response**, inside the **eight-second** total budget for the entire Bitcoin cycle. Retained entries are reused; disappearances never constitute confirmation evidence. After **ten minutes since the full load**, the next renewal reloads the entire baseline. An error, partial response, entry disappearing during its read or exceeded bound invalidates this attempt's public complete ranking with an explicit fallback. After a network, HTTP, RPC, timeout or size error during reconciliation, the previous private index remains until its ten-minute deadline, allowing retry of identifiers and new metadata without downloading the full baseline again. Partial metadata from the failed attempt is discarded. Invalid data, wrong network, initial-load error, inconsistent clock or expired baseline clears the index: the next attempt rebuilds a complete baseline. These successive calls are not an atomic pool snapshot. The ranking means the highest rates in the last successfully reconciled inventory, not a guarantee about the network at display time. Blocks, recommended fees and evidence still come from `BITCOIN_API_URL`, so combined provenances are stated. The complete-ranking count uses the same RPC observation and its independent timestamp.

For **Ethereum**, `txpool_content` uses the same `ETHEREUM_RPC_URL` as blocks, after validating the chain and latest block. The payload groups `pending` and `queued` by sender and nonce under an overall limit of **50,000 transactions**. Only `pending` candidates not already included in the confirmed block and eligible against the observed base fee are ranked by exact effective price in wei before truncation. `queued` entries contribute to `sampling` counts, never to the boarded ranking. Sorting alone does not resolve nonce dependencies: the separate context described above preserves known constraints without changing ranking composition or guaranteeing inclusion. Snapshot `pendingCount` and `mempool` retain the optional `txpool_status` count, received at another time and potentially different.

The PublicNode RPC accepted a pending-transaction filter during a one-off test, followed by an empty read and deletion. This support does not supply the complete removals, evictions and `queued`-category journal needed to maintain a reliable ranking. Ethereum therefore retains **complete reads at least thirty seconds after the previous read finishes**, instead of a ranking made progressively incomplete by arrivals alone. A future incremental strategy must handle full reconciliation, stream loss and provider-node changes.

A server transport reserved for pool reads permits **32 MiB** and **eight seconds per request**, without raising the ordinary two-MiB limit; all calls, validation and ranking in a Bitcoin cycle additionally share the total eight-second budget above. Destinations remain fixed by validated server configuration, never by visitors. A read starts in the background and does not delay the blockchain response; only one complete-pool collection may be in flight per chain, and **at least thirty seconds after completion** separates successful collections. An observation older than thirty seconds is no longer presented as a current complete ranking. Bitcoin also waits thirty seconds after failure; Ethereum waits sixty seconds, or five minutes after RPC refusal. Diagnostics limited to category changes log only the phase and error type, plus the addition count and 500 budget if exceeded; no URL, RPC payload, raw error or stack is exposed. Network, memory and CPU costs remain to be measured under controlled conditions; no additional service, dependency or durable storage is introduced.

Optional nullable `Snapshot.sampling` supplies `{ method, source, observedAt, pendingCount, queuedCount?, update? }` only for a usable complete observation. `method` is `getrawmempool` on Bitcoin or `txpool_content` on Ethereum; Bitcoin requires `update: 'full' | 'incremental'` to distinguish the full baseline from reconciliation, while Ethereum requires `queuedCount`. Counts describe the complete observation, not the up to 1,920 passengers; `observedAt` dates the last successfully reconciled identifier inventory in milliseconds for Bitcoin, or the complete Ethereum receipt. The source is a sanitized label. Demonstration, unavailability or fallback cannot carry a fake complete observation. See the [HTTP contract](../docs/api.md).

Sources: [Bitcoin Core `getrawmempool`](https://bitcoincore.org/en/doc/30.0.0/rpc/blockchain/getrawmempool/), [`getmempoolentry`](https://bitcoincore.org/en/doc/30.0.0/rpc/blockchain/getmempoolentry/), [Geth `txpool_content`](https://geth.ethereum.org/docs/interacting-with-geth/rpc/ns-txpool#txpool-content), [Geth transaction events](https://geth.ethereum.org/docs/interacting-with-geth/rpc/pubsub). This REST fallback retains its bound of 1,000 validated entries; it does not artificially fill the 1,920 limit. If that sample is also unavailable, valid blocks and indicators remain displayable with explicit coverage. The count represents the provider's mempool; the card's fees are its estimate for about thirty minutes, while passengers use their own fee/vsize. Blocks use `weight / 4` in virtual bytes; capacity is one million vB.

To relate sampled passengers to real blocks, the service retains at most **4,096 identifiers per chain for thirty minutes** after their latest observation. Bitcoin checks presence through `/block/{hash}/txids`, including intermediate blocks needed for catch-up. Only exact matches become `confirmed` evidence with the associated hash. Tracking temporarily retains at most 4,096 older observations and 1,920 new ones, or **6,016 identifiers**, while checking inclusions before eviction caused by the new ranking; it returns to 4,096 before responding. The current ranking remains displayed independently of room in this memory. An actually renewed observation updates its timestamp; disappearance does not extend retention and proves neither confirmation nor current mempool presence. Sources: [Esplora contract](https://github.com/Blockstream/esplora/blob/master/API.md#get-blockhashtxids), [mempool.space Bitcoin routes](https://github.com/mempool/mempool/blob/master/backend/src/api/bitcoin/bitcoin.routes.ts).

Block identifiers are validated and the Bitcoin list is limited to 30,000 entries under the two-MiB network limit. An incomplete, duplicate or invalid list produces no confirmation. Failure of this optional verification preserves other live data with explicit coverage. Missing blocks remain retryable: catch-up examines at most **eight blocks per collection**, without inferring confirmation from a gap. A verified empty entry is distinct from an unverified block.

Optional `Snapshot.inclusions` retains up to **sixteen blocks and 4,096 total inclusion identifiers**. It contains `{ block, transactionIds }`, only for tracked observations actually found in that block. It is replayed in later responses and not consumed by a visitor's read. A response contains at most 1,944 current transactions (1,920 pending and 24 reserved confirmations) and three displayed blocks; the inclusion journal is additional. Inclusion hashes and heights must be unique and consistent with displayed blocks at shared heights. No unsampled transaction is invented to fill a wagon.

This memory is instance-local, volatile and bounded. Recovery after restart, a long interruption, expiry or eviction does not guarantee recovery of every confirmation. A reorganization invalidates evidence incompatible with verified hashes; an observed inclusion does not guarantee finality. A backward latest-block movement may cancel higher departures still queued or preparing in the scene, while allowing an already-moving vehicle to finish.

Ethereum verifies `eth_chainId = 0x1`, reads the latest complete block and up to two preceding headers for display. Provider in-memory tracking also examines necessary intermediate blocks within eight checks per collection, then matches their transactions against tracked identifiers. Evidence uses the hash of the block actually read and feeds the same rolling journal. [Official methods: Ethereum JSON-RPC](https://ethereum.org/developers/docs/apis/json-rpc/).

The `pending` tag is optional: a result equal to the latest confirmed block, invalid or unsupported leaves confirmed transactions visible. A distinct candidate block can supply pending passengers; it never represents the global mempool and its count never replaces an unavailable local total. All validated candidate transactions are sorted by exact effective gas price in wei before Gwei conversion and limitation to at most the highest 1,920. Transactions already included in `latest` are excluded before sorting. This ranking concerns only the provider's candidate. Sizes are block gas and transactions' declared gas limits, never estimates from execution receipts.

## Native value of the complete latest block

Optional nullable `Snapshot.latestBlockValue` publishes `{ blockHash, blockHeight, amount, unit, method, transactionCount, observedAt }`. `amount` is a canonical decimal integer string of **at most 83 digits**, exact in minimum units `sat` or `wei`; no floating-point addition computes this aggregate. The hash follows chain format; height, count and date are nonnegative safe integers, and `observedAt` is Unix milliseconds. The schema pairs `sat` with `bitcoin-output-sum` and `wei` with `ethereum-transaction-value-sum`, then requires the same hash, height and complete count as `blocks[0]`. A stale snapshot retains its observed block's date and aggregate. Demonstration and unavailability cannot carry a non-null real aggregate.

Bitcoin uses the optional `extras.totalOutputAmt` field from the enriched block already received through `/v1/blocks`. Separate validation requires a nonnegative safe integer before exact string conversion. If missing, over the bound or invalid, the aggregate is `null` without degrading valid blocks and indicators. ## Independent USD prices

`marketPrices.ts` reads only `https://api.coinbase.com/v2/prices/BTC-USD/spot` and `https://api.coinbase.com/v2/prices/ETH-USD/spot`. These fixed public routes require no key and are not browser-selected. The reader validates `data.base` against the chain, `data.currency = USD` and `data.amount` as a decimal string of at most forty characters; the final number must be positive, finite and no greater than one billion. [Coinbase price contract](https://docs.cdp.coinbase.com/coinbase-app/track-apis/prices).

Both price caches are shared by an instance's visitors and retain a **sixty-second delay after each attempt**, successful or failed, with one concurrent request per chain. Each request retains the eight-second HTTP timeout with a reduced **16 KiB** limit. No price call every three seconds is added. After failure, the last valid price remains usable for up to **five minutes after receipt**, marked `stale`; beyond that or without a valid price, it becomes `null`.

`SnapshotService` reads this cache independently of blockchain collection and adds optional nullable `usdQuote = { usdPerCoin, observedAt, source: 'Coinbase', status }` to the response. `observedAt` is millisecond receipt time, not market time. Renewal starts in the background and the reader immediately returns the last still-usable price or `null`; a later read can retrieve the new price. Neither collection delay nor failure blocks the blockchain response or changes its state. Demonstration mode does not read prices and cannot carry a non-null live price. `fetcher`, clock and USD reader are injectable; injecting only blockchain providers does not trigger a real Coinbase read.

With an active Bitcoin candidate, the interface prefers its complete `medianFeeSats` when supplied, with candidate count and provenance. Without this aggregate, it calculates the median estimated costs of pending transactions in the received sample, in BTC/ETH or USD per transaction at the received price. It then states the count and limits of this high-fee-biased sample. For Ethereum, multiplication uses declared gas limit, not consumed gas or paid fees. Recommended or base native rates remain available; sorting and colors remain intact. Native display of the GBT median preserves half a satoshi; USD conversions remain approximate. No new dependency or environment variable is added. On a HEG server, allow outbound HTTPS to `api.coinbase.com:443` for this conversion; a network refusal leaves native fees usable.

## Configuration and limits

| Variable                    | Default                               | Validation                                                                 |
| --------------------------- | ------------------------------------- | -------------------------------------------------------------------------- |
| `HOST`                      | `127.0.0.1`                           | Bind host; use `0.0.0.0` in Docker                                         |
| `PORT`                      | `3001`                                | Integer 1 to 65535                                                         |
| `BITCOIN_API_URL`           | `https://mempool.space/api`           | Server-only URL, without query, credentials or fragment                    |
| `BITCOIN_RPC_URL`           | `https://bitcoin-rpc.publicnode.com`  | Server complete-mempool RPC; empty disables it, same rules as Ethereum RPC |
| `ETHEREUM_RPC_URL`          | `https://ethereum-rpc.publicnode.com` | Server-only URL, without credentials or fragment                           |
| `TRUSTED_PROXY_IPS`         | empty                                 | At most 64 comma-separated exact IPv4/IPv6 addresses, no CIDR              |
| `API_RATE_LIMIT_PER_MINUTE` | `120`                                 | Integer 1 to 10000 per validated client address                            |

HTTPS is mandatory for external providers. HTTP is accepted only for `localhost`, `127.0.0.1` and `[::1]`. Redirects are refused. URLs are never received from the browser. An RPC URL may contain a key in its path or query, which remains server-side.

Ordinary external HTTP requests have a maximum eight-second timeout and two-MiB response, even without `Content-Length`. Only the complete-mempool reader has the separate 32-MiB limit above; `txpool_status` counters retain 64 KiB and prices 16 KiB. The short Bitcoin projection connection closes after its first response, eight seconds or an error; only text messages are accepted, with at most eight messages and two MiB cumulative before deserialization, and a list bounded to 30,000 unique identifiers. Its URL comes exclusively from validated server-side Bitcoin configuration; the browser opens no provider stream. This projection reader remains separate from the persistent shared streams above; Node 24 supplies their WebSocket transport without another dependency. Injecting HTTP transport for fixtures triggers no real WebSocket; the projection reader can be injected separately.

Two shared caches, one per chain, deduplicate simultaneous reads by every visitor, including projection reads. The minimum delay after each successful or failed refresh is three seconds; only one collection may be in flight per chain. This delay does not guarantee freshness every three seconds: request and catch-up time add to it. A stale snapshot expires after 120 seconds. Output displays at most 1,944 transactions (1,920 pending and 24 reserved confirmations) and three current blocks, plus the journal bounded to sixteen blocks and 4,096 identifiers. Each external request retains its timeout and size limit; successive checks may lengthen collection. Catch-up does not launch one call per visitor.

`X-Forwarded-For` is always ignored. `X-Real-IP` is used only when the proxy socket address is explicitly listed in `TRUSTED_PROXY_IPS` and the header contains one valid IP. The proxy must replace this header itself. In Docker, configure the address actually observed on the Docker network, not automatically 127.0.0.1. Without a trusted proxy configured, visitors behind the same proxy share its quota. Also add a limit at the public reverse proxy.

Files from `dist/` are served with CSP, rejection of hidden paths and directory traversal, symbolic-link checking and SPA fallback restricted to extensionless routes. API routes permit no signing, wallet connection or transaction broadcast.
