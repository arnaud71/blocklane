# BlockLane — observatoire blockchain HEG

La scène distingue désormais inventaire du fournisseur, candidat Bitcoin et observations historiques. Le suivi du pool Bitcoin continue pendant GBT ; Ethereum possède une référence de base fee pour la projection suivante et des motifs d’attente explicites. Les animations restent une représentation bornée, sans prétendre connaître le mempool mondial ou les choix privés des producteurs. Voir [la décision d’architecture](docs/architecture.md) et [les vérifications](docs/validation.md).

Une ville animée pour comprendre Bitcoin et Ethereum : les transactions deviennent des voyageurs, les blocs des transports. Une interprétation originale de l'esprit de [TxStreet](https://github.com/txstreet/txstreet), avec des voyageurs en Canvas 2D natif, une ville SVG, une interface française et un socle conçu pour rester maintenable.

Le panneau Bitcoin propose aussi une rubrique **Comparaison** : candidat observé avant la détection du bloc contre transactions réellement incluses, avec trois catégories et un périmètre complet hors coinbase. Le détail **Bloc** précise sources, dates et totaux. Sans candidat préalable valide, le bilan reste indisponible ; une transaction prévue mais non incluse dans ce bloc n’est pas déclarée encore en attente.

Sur Ethereum, les dépendances de nonce connues dans le pool complet restent prises en compte même si le prédécesseur est hors de l’échantillon affiché. Les motifs distinguent parent en attente, queued, nonce manquant et état inconnu. Une absence ne vaut pas inclusion ; un prédécesseur jamais observé reste annoncé comme une limite de l’estimation. Ce suivi réutilise les données déjà collectées, sans nouvel appel RPC.

L'application démarre en mode **direct**. Bitcoin et Ethereum sont visibles ensemble dans une ville qui occupe la fenêtre. La démonstration pédagogique est un mode séparé, annoncé à l'écran. Une source indisponible ne déclenche jamais une simulation présentée comme réelle.

La composition utilise toute la largeur du desktop : une seule rangée de maisons et de bâtiments HEG au centre, Bitcoin à gauche et Ethereum à droite. De chaque bord vers le centre, les colonnes sont **arrivées, file d'attente, couloir de déplacement, wagons, puis maisons communes**. Les nouveaux voyageurs entrent horizontalement par le bord gauche pour Bitcoin et le bord droit pour Ethereum. Les portes sont du côté des quais extérieurs, à gauche des wagons Bitcoin et à droite des wagons Ethereum ; les trajets ne traversent jamais la chaussée.

L'espace supplémentaire élargit les quais et leurs colonnes, avec des wagons et des personnages gardant leurs proportions. Les grands panneaux restent au-dessus des scènes et la hauteur de leurs lignes est partagée entre les deux réseaux. Le campus se compacte sur les petits écrans. Les résultats des contrôles de cette disposition et leurs limites figurent dans [docs/validation.md](docs/validation.md).

Une petite borne **Réseau — hors échantillon**, illustrée par des nœuds reliés, se trouve tout en haut du bord extérieur de chaque quai. Elle s’éclaire, ouvre sa porte avant l’apparition des nouveaux voyageurs réseau et la maintient ouverte après leur passage. Ces voyageurs rejoignent le premier wagon par une voie au-dessus de la file pendant la préparation : trois secondes pour Bitcoin, 1,5 seconde pour Ethereum à vitesse normale. Leur traînée reste réservée à ce passage réseau. Les arrivées nombreuses sont échelonnées et réparties en éventail au-dessus de la file, pour rendre le groupe visible tout en gardant la même échéance de départ. Les arrivées ordinaires restent plus bas et les voyageurs déjà connus gardent leur position ; les transactions du bloc sans détails individuels restent un complément collectif, hors coinbase Bitcoin, sans faux identifiants. Ce repère illustre les limites de notre observation et ne mesure pas un mempool mondial. Voir [les règles d’animation](docs/animation.md).

Dans la file d'attente, les voyageurs utilisent les places libres avant de se superposer. Les places sont espacées selon la largeur du quai et libérées à l'embarquement. La file active possède neuf rangées ; une zone « Observations » en bas du quai possède trois rangées distinctes pour les statuts inconnus, absents ou remplacés. Les personnes déjà en attente gardent leur place, les nouveaux arrivants prennent les places restantes par frais décroissants. Un retour du wagon réserve une nouvelle place libre si l'ancienne a été reprise. Les contrôles ciblés et leurs limites figurent dans [docs/validation.md](docs/validation.md).

La rubrique **Flux** des panneaux du haut privilégie les événements reçus par une connexion partagée côté serveur : ajouts Bitcoin et notifications pending Ethereum, avec durée mesurée, débit moyen et mini courbe. Bitcoin intègre désormais jusqu’à **384 vraies arrivées identifiées dans son plafond de 1 920 transactions pending**, avec leurs frais et leur taille ; son groupe latéral « +X hors échantillon » est supprimé. Ethereum conserve ce signal collectif. Les inventaires complets périodiques restent un secours nommé séparément. Initialisation, coupure, dépassement de limite et zéro reçu sont distingués ; une notification Ethereum peut être une promotion ou une réémission, sans confirmer une inclusion ou mesurer un flux mondial.

## Démarrer

Runtime requirement: **Node.js 24.22.1 or newer in the 24.x LTS line**, with npm. The checked-in `.nvmrc` selects the verified security release; with nvm, run `nvm install` and `nvm use` before installing dependencies. Earlier Node 24 versions are rejected by the existing strict engine policy. See the [security maintenance review](docs/maintenance-2026-10-26.md).

```sh
npm ci
cp .env.example .env
npm run dev
```

Ouvrir `http://localhost:5173`. Vite transmet les appels `/api` au serveur local sur le port `3001`. Les accès aux fournisseurs passent par ce serveur ; une clé RPC éventuelle reste hors du navigateur.

```sh
npm run build
npm start
```

Le serveur sert alors l'interface compilée et l'API sur `http://127.0.0.1:3001`. Le mode direct exige un accès réseau sortant vers les fournisseurs configurés.

## Données et portée

Bitcoin utilise en priorité le **candidat proposé par le nœud via `getblocktemplate`** : le premier wagon est réservé aux membres connus de ce candidat, le second reste une estimation. Une observation historique hors candidat peut rejoindre le second wagon ou attendre sur le quai, même s'il reste de la place dans le premier. Quand le candidat est indisponible, les deux wagons reprennent l'estimation habituelle selon les frais et la capacité native. En estimation, une hausse de la recommandation Bitcoin ou une simple disparition de l'échantillon ne retire pas à elle seule la place d'un voyageur déjà embarqué ; Ethereum conserve son critère d'éligibilité à la base fee observée.

Jusqu'à 1 920 anciennes observations peuvent rester individualisées. L’expiration de leur candidature après 30 minutes ne retire pas automatiquement leur silhouette du quai : sous ce budget, elle peut rester visible plus longtemps. Celles ayant déjà embarqué peuvent garder leur candidature après une descente temporaire ; un membre connu du candidat Bitcoin peut aussi être admis depuis le quai sans ancien embarquement. Ces voyageurs portent une horloge, conservent leur dernière date réelle et ne certifient aucune présence actuelle dans le mempool. Les compteurs des projections estimées les incluent ; celui du candidat Bitcoin complet garde son total propre. Les métriques du fournisseur et la médiane des frais restent fondées sur les relevés actuels. À réception d'un bloc, seules les inclusions vérifiées partent avec lui : une proposition `getblocktemplate` ne constitue jamais cette preuve.

Une inclusion réellement vérifiée retire son voyageur après le départ, ou immédiatement en mouvements réduits ; une ancienne réponse `pending` ne le réintroduit pas pendant la conservation de sa preuve. Ethereum rapproche aussi les nouvelles observations des blocs récemment lus et vérifie progressivement des observations anciennes par reçus, avec un budget partagé et limité côté serveur. La preuve doit correspondre au hash demandé et à un bloc canonique contenant cet identifiant. Un reçu absent laisse le statut inconnu. Ce rattrapage reste limité aux identifiants encore suivis par le serveur ; un redémarrage perd ce suivi, sans inventer le statut des anciens personnages conservés uniquement par le navigateur. Les limites et vérifications sont décrites dans [l'architecture](docs/architecture.md) et [la validation](docs/validation.md).

| Réseau   | Source initiale                                           | Ce que l'on peut montrer honnêtement                                                                                                                   |
| -------- | --------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Bitcoin  | API mempool.space et RPC Bitcoin PublicNode, remplaçables | Candidat du nœud via `getblocktemplate` en priorité ; secours par pool complet, projection puis transactions récentes ; blocs et preuves mempool.space |
| Ethereum | JSON-RPC public PublicNode, remplaçable                   | Blocs récents ; top frais du pool `pending` via `txpool_content` si disponible, sinon bloc candidat ; compte local facultatif                          |

Les sources publiques sont partagées et n'offrent ici aucune garantie de disponibilité. Une application publique durable devrait utiliser un contrat fournisseur adapté ou des nœuds administrés. Les données Ethereum ne constituent **pas un mempool mondial exhaustif** : les nœuds ont une vue locale et certaines transactions suivent des canaux privés. Voir les explications de [consensus Ethereum](https://ethereum.org/developers/docs/consensus-mechanisms/pos/) et le contrat [JSON-RPC](https://ethereum.org/developers/docs/apis/json-rpc/).

Le serveur demande d’abord un candidat Bitcoin par `getblocktemplate`, avec les règles SegWit, au RPC configuré. Il transmet jusqu’à **1 920 détails individuels courants au total**, dont jusqu’à **384 arrivées récentes réelles** reçues par `track-mempool`, puis complète avec la sélection issue du candidat ou des replis. La sélection de base peut aussi utiliser les détails hors candidat du pool RPC indépendant ; les arrivées prioritaires peuvent réduire la part transmise de ces autres composantes. Ce mélange n’est pas un top global. La réserve du flux conserve uniquement identifiant, frais propres et taille, sans appel HTTP par identifiant ni conservation des inputs ou outputs. Elle expire après soixante secondes sans delta consécutif validé et se vide à la coupure ou à la resynchronisation. `bitcoinArrivals` annonce sa source, sa date et les identifiants pending effectivement transmis, indépendamment du relevé RPC. Les nouveaux voyageurs entrent par le côté ordinaire ; un détail remplacé peut rester dans les observations historiques selon les bornes existantes.

`blockTemplate` conserve séparément la source, la date, la hauteur prévue, le parent, le nombre complet de transactions hors coinbase, le poids, sa limite et la médiane complète des frais proposés. Ses identifiants sélectionnés comprennent aussi les membres encore connus du suivi borné, pour rapprocher les voyageurs historiques du candidat. Le premier wagon à l’arrêt représente le candidat complet par ces personnages et un groupe statique pour les autres transactions : aucun détail individuel n’est inventé pour ce groupe. Une arrivée hors candidat ne rejoint pas automatiquement ce premier wagon. Cette proposition dépend de la vue et de la politique du nœud ; elle ne prouve ni qu’un pool minier travaille dessus, ni que ces transactions seront incluses.

Ce lecteur fonctionne **côté serveur en arrière-plan**, avec une seule tentative en cours et au moins 15 secondes entre sa fin et la suivante. Il contrôle le réseau annoncé, la synchronisation, le parent, la hauteur, les identifiants, les dépendances et les poids ; il limite la réponse à **16 Mio**, le candidat à **30 000 transactions** et l'ensemble de la tentative à **huit secondes**. Les octets bruts restent côté serveur et ne sont pas conservés pour l'animation. Ces contrôles ne constituent pas une validation de consensus complète. Un candidat doit correspondre à la tête observée et avoir au plus **30 secondes** : après expiration, changement de parent, erreur ou réponse incohérente, son libellé est retiré et le repli est annoncé. L'interface applique aussi cette expiration en temps réel, même pendant une requête lente ou une animation en pause, sans redater les observations ni ajouter de requête. Un candidat valide vide reste distinct d'un candidat indisponible.

Le **secours Bitcoin** suit cet ordre : top frais du pool complet du RPC par `getrawmempool`, transactions du premier bloc projeté mempool.space, puis transactions récentes de cette API. Le pool charge d'abord `getrawmempool(true)`, puis réconcilie les identifiants et ne récupère que les métadonnées des nouveaux arrivants, au moins 30 secondes après la fin de la collecte précédente. Un recalage complet reste prévu après dix minutes, une donnée invalide ou un mauvais réseau. Un échec incrémental retire le classement public et garde seulement l'index privé encore valide pour réessayer sans retélécharger toute la base. Les classements de secours utilisent les frais propres des transactions, sans reproduire la sélection par paquets et dépendances d'un producteur. Les blocs, frais conseillés et preuves d'inclusion restent issus de mempool.space ; ces provenances sont annoncées séparément. Le repli REST `/mempool/recent` garde sa limite de 1 000 entrées validées ; il peut donc fournir moins de 1 920 détails.

Ethereum conserve `txpool_content` du RPC configuré : les 1 920 candidates au maximum proviennent des transactions `pending` éligibles à la base fee observée ; les `queued` sont comptées séparément et ne montent pas dans les wagons. Si cette lecture n'est pas exploitable, le repli annoncé utilise le bloc `pending` du fournisseur. Les collectes de pools restent en arrière-plan, avec une seule lecture en cours par lecteur et au moins 30 secondes après sa fin ; elles ne retéléchargent pas le pool toutes les trois secondes. Leur transport distinct reste plafonné à **32 Mio**, les autres requêtes ordinaires à deux Mio. Le relevé Bitcoin est compacté pour les réconciliations ; Ethereum renouvelle une lecture complète et conserve ses candidates au plus 30 secondes. Un filtre d'arrivées seul ne fournit pas les retraits, évictions et changements `queued` nécessaires à un classement complet fiable. Ces relevés restent locaux, non atomiques et sans top mondial. Le coût réseau et mémoire est borné mais non mesuré ; les observations réelles et contrôles documentés restent consultables dans [docs/validation.md](docs/validation.md).

La scène représente un échantillon borné, pas toutes les transactions du réseau. L'animation illustre les mécanismes ; elle ne prédit pas l'ordre exact d'inclusion ni le prochain bloc. Les frais indiqués sont des observations ou des estimations, jamais une garantie d'inclusion.

Depuis la correction du 15 octobre 2026, les projections utilisent la **taille des transactions et la capacité du bloc**, et non un budget de 96 unités. Bitcoin additionne les tailles virtuelles en vBytes face à une capacité de 1 000 000 vBytes ; avec un candidat du nœud, le premier wagon respecte aussi sa limite de poids divisée par quatre. Ethereum additionne les limites de gas déclarées face au `gasLimit` du dernier bloc observé : c'est une estimation prudente, distincte du gas effectivement consommé. Une capacité Ethereum absente reste inconnue. Les 96 emplacements dessinés, sur huit colonnes et douze rangées, servent uniquement à répartir les personnages ; ils peuvent se superposer et ne limitent plus le nombre de transactions embarquées.

La plaque à l'arrière distingue les périmètres. Avec un **candidat Bitcoin actif**, le premier wagon affiche son **compte complet hors coinbase** et `100 × weight / weightLimit` ; sa taille virtuelle vaut `weight / 4`. Ces valeurs décrivent la proposition, pas un bloc miné. Le groupe « transactions groupées » vaut le compte complet moins les membres connus individualisés dans toute la scène, y compris ceux encore sur le quai : leur embarquement ne les compte donc pas deux fois. Un candidat de 5 000 transactions et de 3 992 000 WU sur 4 000 000 WU affiche **5 000 TX et 99,8 %** ; avec 960 membres individualisés, 4 040 restent groupées. Les projections estimées conservent **`N TX · ≈P %`**, calculé sur les seuls voyageurs effectivement à bord, hors réservations encore sur le quai. Pendant la préparation et le départ, le groupe disparaît : le premier wagon utilise le pourcentage du **bloc réel complet**, `Block.used / Block.capacity`, tandis que son compteur TX reste celui des voyageurs aux inclusions connues. Les infobulles et libellés accessibles explicitent ces différences. Le repli ou l'expiration du candidat retire aussi le groupe et rend leurs anciens compteurs aux estimations. Aucune transaction individuelle, aucun statut ni aucune preuve ne sont créés pour compléter le candidat. Les résultats des contrôles et leurs limites sont consignés dans [docs/validation.md](docs/validation.md).

Depuis l’extension du 16 octobre 2026, chaque chaîne peut afficher jusqu’à **1 920 voyageurs en attente**, contre 960 auparavant. Les classements de base privilégient les frais élevés ; la sélection Bitcoin courante intègre aussi sa réserve d’arrivées réelles. Jusqu’à 24 confirmations vérifiées restent réservées séparément : la réponse est bornée à **1 944 transactions**. La file conserve ses colonnes adaptatives, neuf rangées actives et trois historiques ; les places valides restent stables dans une même zone et les superpositions restent possibles. Un fournisseur exposant moins de candidates produit un échantillon plus petit, sans voyageur fictif ajouté en direct. La démonstration utilise 1 920 transactions en attente et 12 confirmations simulées par chaîne, soit 1 932 transactions. Le cache reste à trois secondes et cette extension n’ajoute aucun appel fournisseur. La réserve historique reste fixée à **1 920 observations**, indépendamment du plafond courant : les résidents ordinaires sont bornés à **3 840** et l’archive à 512 identifiants. Les capacités natives des blocs, les 96 emplacements visuels des wagons et les budgets Canvas restent conservés. Les bornes temporaires figurent dans [l’architecture](docs/architecture.md), et les contrôles et leurs limites dans [docs/validation.md](docs/validation.md).

Les voyageurs individuels sont dessinés sur un **Canvas 2D transparent par rue**, à la place de leurs nombreux éléments SVG. Les panneaux et contrôles restent en React ; les bus, portes, phares, textes, maisons et groupes collectifs statiques restent en SVG. Un cache borné de petites images préparées réutilise les têtes, torses et icônes ; les membres et flèches gardent leurs gestes et orientations. Les couleurs des frais et la taille des têtes restent conservées ; les couleurs sont actualisées directement, sans l'ancienne transition CSS de 300 ms. La même horloge pilote la scène, sans boucle d'animation supplémentaire et sans nouvelle dépendance.

Le départ réutilise aussi une image préparée de tous les occupants du premier wagon, avec leurs découpes intérieures, puis déplace cette image avec le véhicule. Il évite ainsi de redessiner chaque voyageur embarqué à chaque image du trajet. Ce cache ajoute au plus une surface d'un million de pixels par rue, limitée à 2 048 pixels par dimension ; il est libéré après le départ ou au démontage. Si sa création échoue, tous les occupants gardent leur dessin individuel. Les voyageurs du quai et du wagon suivant continuent leurs déplacements ordinaires. La préparation d'au moins une seconde, les portes et les preuves d'inclusion gardent leurs règles. Cette optimisation locale reste non validée et son gain n'est pas mesuré dans les contrôles documentés à ce jour.

La sélection reste possible au pointeur et par une commande HTML pour parcourir les transactions, choisir un identifiant et afficher ses détails au clavier. Les voyageurs historiques individualisés restent sélectionnables : leurs détails distinguent ancienne observation et présence actuelle attestée ou inconnue. Le bouton **Transactions** propose une recherche par hash ou fragment et des filtres **Présentes**, **Différées**, **Historiques** et **Incluses**, sans masquer les personnages du Canvas. Les statuts sont communs à la liste, à l’infobulle et au panneau. Une couleur rouge peut refléter des frais anciens, sans priorité actuelle garantie. Les groupes collectifs sans suivi individuel restent décoratifs. Le dessin reproduit les portes, les zones intérieures et le miroir Bitcoin ; l’échantillon courant de 1 920 voyageurs, la grille visuelle de 96 emplacements et les bornes de résidents et d’archives sont conservés. La résolution du Canvas est plafonnée à un ratio de pixels de 2, quatre millions de pixels et 8 192 pixels par dimension ; une indisponibilité de Canvas est annoncée explicitement et les informations HTML restent accessibles.

Les libellés de frais, les formats numériques et les médianes réutilisent leurs calculs lorsque leurs entrées sont inchangées. Les effectifs du panneau sont transmis au plus toutes les 250 ms, séparément des mouvements de la scène à environ 24 images par seconde. Des délais ponctuels conservent l'expiration du cours USD et du pool Ethereum même lorsque la scène reste immobile, sans intervalle ni appel réseau supplémentaire. Le cache API reste à trois secondes. Aucun profilage ni mesure de gain n'est effectué ; la migration Canvas et ces optimisations restent non validées dans les contrôles documentés à ce jour.

Le sélecteur **Vitesse** propose **0,5×, 1×, 2×, 5× et 10×** pour les voyageurs et les wagons. Ce facteur accélère leur horloge d'animation, y compris la préparation et les trajets ; les collectes API, le cache de trois secondes, la fraîcheur des données et le temps réel depuis le dernier départ gardent leur rythme. Pause, onglet masqué et mouvements réduits restent respectés.

Un **grand panneau d'informations** reste visible **en haut de chaque blockchain**, dans son en-tête à la place des métriques statiques, et change de rubrique toutes les **4 secondes** : Mempool, Frais médians, Bloc, Valeur et Voyageurs, avec une sixième rubrique Comparaison pour Bitcoin. Le même panneau se compacte selon l'écran ; il laisse le décor SVG, la chaussée et le quai disponibles pour la scène. Les rubriques et la pause du défilement restent accessibles manuellement. La pause générale, les mouvements réduits, une sélection, un onglet masqué ou une source ancienne ou indisponible arrêtent la rotation ; ils ne transforment pas les observations en données nouvelles. Le panneau de détails conserve également sa sélection et propose ses pages avec ce rythme de quatre secondes. Les lectures et le cache de l'API blockchain restent à **3 secondes**.

La rubrique **Valeur** affiche le total du dernier bloc en **BTC ou ETH**, indépendamment du switch des frais, avec un équivalent USD approximatif secondaire lorsqu'un cours utilisable est disponible. Ce total couvre le bloc complet, pas uniquement les voyageurs de l'échantillon. Bitcoin utilise `totalOutputAmt` des statistiques mempool.space : somme des sorties hors transaction coinbase, **monnaie rendue incluse**, sans mesurer un transfert économique net. Ethereum additionne les champs `value` déclarés de toutes les transactions du bloc : les tokens, mouvements internes et frais sont exclus, et la valeur d'une transaction échouée peut être incluse faute de lecture des reçus. Les sommes sont conservées exactement en satoshis ou wei, comme chaînes décimales calculées avec `BigInt`, et liées au hash, à la hauteur et au nombre de transactions du dernier bloc. Une donnée absente ou incohérente affiche **non mesurée**, jamais zéro par défaut ; la démonstration ne reçoit aucun total réel inventé. L'équivalent USD utilise le cours spot reçu, pas un cours historique du bloc. Cette mesure réutilise les fournisseurs existants sans nouveau service réseau.

La rubrique **Mempool** montre le nombre de transactions dans la vue locale du **fournisseur observé**, distinct du nombre de voyageurs de notre échantillon. Elle ne concerne pas un nœud installé sur le Mac et ne prétend pas donner un total mondial. Avec un échantillonnage complet Bitcoin, le compte et sa date viennent du même relevé RPC PublicNode ; avec `getblocktemplate` ou un repli projection/récentes, le compte vient de mempool.space. Le nombre de transactions du candidat n'est jamais utilisé comme taille du mempool. Ethereum conserve le comptage facultatif `pending + queued` de `txpool_status`, avec détail et heure d'observation propres ; les comptes du relevé `txpool_content` utilisé pour le classement restent séparés dans `sampling`. Cette lecture se fait en arrière-plan, au plus une tentative toutes les 30 secondes après la précédente, sans attendre sa réponse pour servir les données blockchain. En cas de panne, le dernier compte est signalé comme ancien et conservé au plus 120 secondes ; passé ce délai, ou si la méthode n'est pas disponible, la valeur devient **non mesurée**. Un compte inconnu n'est jamais remplacé par la taille de l'échantillon ou par un faux zéro. La démonstration distingue ses valeurs simulées du direct. Voir [le contrat HTTP](docs/api.md) pour les champs et limites.

Une **file globale · fournisseur** reste visible en bas de chaque rue, sous la scène et au-dessus de sa couverture. Elle représente collectivement tout le compte local fourni, avec son total exact, sa provenance et le détail `pending + queued` pour Ethereum. « Globale » décrit ici la file complète de ce fournisseur, jamais l'ensemble du réseau. Jusqu'à 48 petites silhouettes sont dessinées par chaîne, avec une échelle commune Bitcoin/Ethereum choisie parmi `1, 2, 5 × 10ⁿ` pour contenir le plus grand total affiché ; la dernière silhouette représente seulement le reste éventuel. L'échelle est annoncée explicitement. Ces groupes statiques n'ont ni identifiants ni frais individuels et ne participent pas aux trajets ou confirmations des voyageurs. Un vrai zéro affiche une file vide ; un compte absent ou expiré reste indisponible, tandis que simulation et ancien relevé restent signalés. La scène garde son échantillon de 1 920 voyageurs et ses anciennes observations séparées. Cette présentation réutilise les données reçues, sans nouvelle API, horloge ou dépendance, et reste non validée dans les contrôles documentés à ce jour.

Les t-shirts passent du jaune pour les frais faibles à l'orange à la moyenne, puis au rouge à partir de deux fois la moyenne des voyageurs en attente affichés sur la même blockchain. Cette moyenne concerne notre échantillon visible, pas tout le réseau.

Les transactions classées comme contrat portent un accessoire **bleu cyan avec des traits foncés**, distinct des t-shirts jaunes. Les têtes présentent des différences de taille accentuées, sur une échelle absolue bornée de 0,8 à 2,5 : vBytes Bitcoin ou limite de gas déclarée Ethereum, sans modifier la taille du corps ni la capacité du bloc.

Les wagons ont des phares avant blanc chaud qui s'allument avant le départ, dès la préparation, et des feux arrière rouges pendant la fin de l'arrivée. Ces lumières suivent les phases de l'animation ; la pause conserve leur état et les mouvements réduits restent statiques.

Après réception du bloc, le premier wagon attend **au moins trois secondes de préparation pour Bitcoin et 1,5 seconde pour Ethereum à vitesse normale**. Les passages et les compléments identifiés entre-temps partagent cette échéance : sorties accélérées de 500 ms au maximum, puis embarquement avec le temps restant pour les voyageurs venant du second wagon. Une sortie déjà engagée est accélérée depuis sa position, sans recommencer son chemin. Le départ attend toujours que toutes les inclusions connues soient à bord et les autres voyageurs hors du premier wagon. Une preuve reçue tardivement garde un passage minimal de 50 ms et peut prolonger l'arrêt ; la pause et la vitesse s'appliquent à cette horloge d'animation. Ce délai ne change ni la collecte ni la finalité du bloc.

Chaque chaîne affiche **« Depuis départ »** dans une ligne fixe sous le grand panneau de son en-tête, quelle que soit la rubrique affichée : le temps réel écoulé depuis le début du dernier départ animé dans cette session. Le compteur avance indépendamment de la pause et de la vitesse ; ce n'est ni l'âge du bloc ni un compte à rebours avant le suivant. Il reste à `—` avant le premier départ, y compris lorsque les mouvements réduits appliquent les confirmations sans trajet. Une animation de rattrapage remet aussi ce compteur à zéro. Une indisponibilité temporaire conserve le dernier départ connu ; un rechargement ou un changement direct / démonstration réinitialise le compteur. En démonstration, il concerne uniquement les départs simulés. Cette présentation n'ajoute aucune requête API et conserve le cache existant.

Les en-têtes et la page Réseau affichent les **frais médians par transaction** avec leur périmètre. Pour un candidat Bitcoin actif dont `medianFeeSats` est fourni, le serveur utilise les frais exacts de **toutes ses transactions hors coinbase**, avant le choix des 1 920 personnages. Avec un effectif pair, la moyenne des deux frais centraux peut valoir une demi-satoshi ; zéro reste une valeur possible, un candidat vide n'a pas de médiane. La mention « Candidat complet » indique ce compte, sans prétendre mesurer la médiane du mempool ou des frais confirmés. Si cet agrégat est absent, le repli utilise la médiane des coûts estimés des seules transactions courantes `pending`, avec effectif annoncé et exclusion des confirmations et observations historiques. Cet échantillon biaisé vers les frais élevés ne constitue pas une médiane du réseau ; une métrique absente affiche `—`.

Une commande commune permet d'afficher cette médiane en **BTC ou ETH par transaction**, ou en **dollars américains par transaction**. La médiane Bitcoin complète est exacte dans sa conversion native, y compris une demi-satoshi ; les coûts estimés de l'échantillon et la conversion USD portent `≈`. Les taux conseillés Bitcoin et la base fee Ethereum restent consultables dans les détails de la page Réseau. En USD, le détail et l'infobulle d'un voyageur donnent aussi un montant total estimé. Pour Ethereum, le calcul utilise le prix du gas observé, pourboire inclus lorsqu'il fait partie de ce prix, multiplié par la limite de gas déclarée ; il ne représente ni le gas réellement consommé ni les frais réellement payés. Les taux arrondis fournis par les adaptateurs rendent les coûts approximatifs. Le classement et les couleurs utilisent toujours les taux natifs.

La conversion utilise un cours spot [Coinbase](https://docs.cdp.coinbase.com/coinbase-app/track-apis/prices) reçu côté serveur, avec sa source et son heure visibles. Ce cours possède un cache partagé de 60 secondes, distinct du cache blockchain de 3 secondes. La collecte du cours s'effectue en arrière-plan sans attendre sa réponse pour afficher les données blockchain : au premier chargement, la conversion peut rester indisponible jusqu'à une lecture suivante. En cas de panne, un cours conservé reste utilisable au plus cinq minutes, puis la conversion devient indisponible sans remplacer une valeur inconnue par zéro. La conversion se fait au cours relevé, pas au cours historique du bloc ; la démonstration ne reçoit aucun cours fictif. Cette extension reste non validée selon les limites des contrôles décrites dans [docs/validation.md](docs/validation.md).

Les anciennes observations regroupées conservent jusqu'à 512 identifiants pendant 30 minutes dans l'interface. Le serveur suit jusqu'à 4 096 identifiants observés pendant 30 minutes et vérifie les nouveaux blocs, avec un rattrapage limité à huit blocs par collecte. Un journal partagé de 16 blocs et 4 096 preuves au total permet de retrouver les inclusions des voyageurs conservés, qui quittent alors le groupe pour le départ correspondant. Au-delà des bornes ou après redémarrage, le suivi individuel reste inconnu ; le groupe ne représente pas un nombre exact de transactions encore en attente sur le réseau.

Le serveur mutualise les appels et attend au moins 3 secondes après chaque collecte avant de pouvoir en lancer une autre. Un dernier instantané valide peut être conservé jusqu'à 120 secondes en étant signalé comme ancien ; au-delà, la source devient indisponible. L'interface attend 3 secondes en direct et 5 secondes en démonstration après chaque réponse avant de consulter à nouveau l'API locale, sans chevaucher ses requêtes. Elle suspend ces lectures dans un onglet masqué. La durée de collecte s'ajoute à ces délais : une nouvelle donnée toutes les 3 secondes n'est pas garantie. Le rythme des blocs et la fréquence d'actualisation de l'interface sont deux choses différentes.

## Configuration

Les variables sont décrites dans [.env.example](.env.example). Ne jamais préfixer une clé fournisseur par `VITE_` : ces valeurs seraient intégrées au code client.

| Variable                    | Valeur initiale                       | Usage                                                                                             |
| --------------------------- | ------------------------------------- | ------------------------------------------------------------------------------------------------- |
| `PORT`                      | `3001`                                | Port du serveur HTTP                                                                              |
| `HOST`                      | `127.0.0.1`                           | Interface d'écoute ; `0.0.0.0` dans le conteneur                                                  |
| `API_RATE_LIMIT_PER_MINUTE` | `120`                                 | Limite de requêtes API par client ; entier de 1 à 10000                                           |
| `TRUSTED_PROXY_IPS`         | Vide                                  | IP exactes des reverse proxies fiables, séparées par virgules                                     |
| `BITCOIN_API_URL`           | `https://mempool.space/api`           | API Bitcoin pour blocs, frais et repli                                                            |
| `BITCOIN_RPC_URL`           | `https://bitcoin-rpc.publicnode.com`  | RPC candidat `getblocktemplate` et pool complet de secours ; valeur vide pour désactiver les deux |
| `ETHEREUM_RPC_URL`          | `https://ethereum-rpc.publicnode.com` | Point d'accès JSON-RPC Ethereum                                                                   |

Les URL sont configurées par l'opérateur, jamais par les visiteurs. HTTPS est requis pour un fournisseur distant ; HTTP est accepté uniquement pour les adresses de boucle locale. Une clé dans une URL reste un secret : protéger `.env`, les journaux et la configuration de l'hébergeur.

La personnalisation HEG se fait dans `src/config/brand.ts` : nom, textes et lien FairOnChain facultatif. Le lien est désactivé par défaut. Le fonctionnement de BlockLane ne dépend pas de FairOnChain. L'identité visuelle actuelle est une proposition, à valider avant d'utiliser des marques ou logos institutionnels officiels.

## Mesurer la scène localement

Le banc de mesure utilise des données contrôlées et intercepte toutes les requêtes API. Après installation des outils de test décrits ci-dessus, lancer dans un terminal :

```sh
npm run build
node node_modules/vite/bin/vite.js preview --host 127.0.0.1 --port 4173 --strictPort
```

Puis, dans un second terminal :

```sh
node --import tsx scripts/benchmark-scene.ts --label mesure-960 --sample-size 960
node --import tsx scripts/benchmark-scene.ts --label mesure-1920 --sample-size 1920
```

Le script vérifie les effectifs, exécute trois répétitions desktop et mobile émulé, puis écrit un rapport dans `.local/performance/<label>/report.json`. Sans `--sample-size`, il utilise le plafond courant de 1 920. Les deux tailles peuvent être comparées sur le même build ; l’historique reste borné séparément à 1 920 individus, donc les cohortes plus grandes provoquent une éviction au lieu d’agrandir cette réserve. Le preview sur 4173 est réservé à ce jeu d’essai ; le direct habituel reste sur 5173. Les API publiques ne participent pas aux mesures. Fermer les autres charges de calcul et conserver les mêmes paramètres pour une comparaison ; les résultats ne constituent pas une garantie de FPS sur d’autres appareils. Voir [les résultats et limites](docs/validation.md).

## Hébergement

```sh
docker compose up --build -d
```

Le conteneur écoute sur le port `3001`, publié seulement sur `127.0.0.1:3001` côté hôte. Il fonctionne sans privilèges et avec un système de fichiers en lecture seule. Pour une ouverture au public, placer un reverse proxy HTTPS devant, limiter les requêtes au niveau du proxy, surveiller le service et conserver une image de retour arrière. Ne pas utiliser le serveur Vite de développement pour héberger le site.

Pour utiliser la conversion USD sur l'infrastructure HEG, autoriser aussi les connexions HTTPS sortantes du serveur vers `api.coinbase.com:443`. Les deux URL de cours sont fixes ; aucune nouvelle variable d'environnement, clé ou dépendance n'est nécessaire.

Configurer `TRUSTED_PROXY_IPS` avec l'adresse du proxy réellement vue par le serveur, et faire remplacer `X-Real-IP` par le proxy. Sans cette configuration, les visiteurs d'un même proxy partagent la limite serveur. Les en-têtes d'un visiteur direct ne sont pas considérés comme une preuve d'adresse ; `X-Forwarded-For` est ignoré.

Recommandation initiale : **un petit serveur Linux ou une plateforme de conteneurs, un seul service Node et des fournisseurs de données remplaçables**. Sans base de données, Redis ni infrastructure blockchain à administrer au départ. Une infrastructure HEG peut héberger le même conteneur. Les options, leurs compromis et les conditions d'évolution figurent dans [docs/architecture.md](docs/architecture.md).

Le code est publié sur [arnaud71/blocklane](https://github.com/arnaud71/blocklane), avec protections de `main` et contrôles CI obligatoires. La mise en ligne de l’application, le domaine, TLS, les comptes fournisseurs et les alertes d’hébergement restent à configurer dans l’environnement retenu. Aucune disponibilité de production n'est promise par cette version initiale.
